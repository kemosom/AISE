01 / Theory

From a specification to software

A software artefact is an output used to build, test, or describe a system. It can be a function, a test suite, or an API specification. In this lab, the artefact is a booking function. The input is a written specification that tells the function which requests to accept or reject.

Input

Specification

Define the inputs, required outputs, and boundary rules. Example: a new booking can start exactly when the previous one ends.

Transformation

Generation

A model reads the specification as tokens and produces an output sequence. In this example the target sequence represents source code.

Evidence

Verification

Derive expected answers from the specification. Run the artefact on the same inputs and compare what it actually returns.

How sequence-to-sequence generation works

In an encoder–decoder Transformer, the encoder represents the input sequence in context. The decoder uses that representation and the tokens it has already produced to generate the next output token. In a code-generation task, the input could be a requirement and the output a function. Code can also be generated by decoder-only models, which receive the prompt as context and continue the sequence. The video explains the encoder–decoder architecture.

What should you evaluate?

Functional correctness

Compare the expected and actual output for each case. Valid syntax lets the code run. Correct behavior requires the output to match the rule. A function can run successfully and still reject a valid request.

Consistency across versions

Run the same tests against both versions. If the outputs differ, check which one follows the specification. If both versions agree, they can still both be wrong. A regression occurs when a previously passing case fails after a change.

Coverage and limitations

A test suite only checks the cases it includes. An ordinary request in an empty room tells you little about a request between two existing bookings. A result such as 6/6 means six cases passed. It does not establish how the system behaves on untested inputs or whether a prompt will always generate a correct function.

02 / Booking game

The last study room

You are the release reviewer. Predict what the feature should do, then reveal how the two implementations behave. Earn a point for each correct first prediction.

Official booking rules
  1. A request must start and end on the same booking day. Midnight at the start is 00:00 and midnight at the end is 24:00.
  2. The end must be strictly later than the start.
  3. Reject requests that overlap any existing booking. A request may touch another booking at either end.

The game uses two fixed teaching implementations to illustrate possible generation errors. Your browser runs both implementations on the test inputs. There is no live model call.
